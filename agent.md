# AGENT.md — Цели, архитектура и задачи проекта

## 1. Общая цель проекта

Написать **32/64-битную операционную систему**, бо́льшая часть которой написана **на Lisp**.

Ключевые принципы:

- **Ядро (kernel)** пишется **только на Carp** (Haskell-диалект Lisp с линейными типами, компилируется в C). Никаких других языков в ядре — только Carp (плюс минимальные asm-обёртки для старта/переключения контекста, если это неизбежно, но их свести к абсолютному минимуму и вынести в отдельный тонкий слой `boot/`).
- **LibOS / пользовательские сервисы и библиотеки** пишутся на **других Lisp-диалектах**: Racket, Clojure/ClojureScript, SBCL/Common Lisp, Guile, Fennel (Lua-dialect Lisp) — по выбору под задачу. Компиляция/рантайм этих Lisp'ов предоставляется инфраструктурой LibOS.
- Система должна поддерживать как **32-бит (x86/i386, ARMv7)**, так и **64-бит (x86_64, AArch64)** режимы.
- Всё остальное (драйверы устройств, стек сети, графика, звук, ФС) строится вокруг проверенных C-библиотек, инкапсулированных в Lisp-обёртки, чтобы основной код ОС оставался Lisp'овым.

Архитектурная парадигма — **экзядро (exokernel, модель MIT ExOS/Aegis)**, НЕ микроядро: ядро не предоставляет абстракций (процессов, файловой системы, сокетов, планировщика) — оно только **безопасно мультиплексирует физические ресурсы** (физическая память, секторы диска, IRQ, порты ввода-вывода/MMIO, кванты времени CPU) между приложениями и предоставляет примитивы защиты. Все абстракции ОС — планирование, виртуальная память, файловые/сетевые/графические/звуковые API, драйверы — живут в **LibOS**, который линкуется в каждое приложение как библиотека («серверная ОС» внутри адресного пространства приложения). Планировщик также полностью в LibOS: ядро лишь переключает контексты по кванту таймера и выполняет запросы LibOS (`bind_time / yield / block`).

## 3. Роль компонентов (внешние библиотеки)

| Компонент | Библиотека | Где живёт | Как интегрируется |
|---|---|---|---|
| USB | **cherryUSB** или **tinyUSB** | LibOS: driver-library (linкуется в приложение, владеющее USB-контроллером) | Lisp вызывает C-API через FFI-шим; приложение получает права на IRQ и MMIO/EHCI/xHCI-порты через экзядро (`irqmap`/`iomap`) |
| Сеть | **lwIP** | LibOS: сетевая библиотека + NIC-драйвер внутри приложения | lwIP raw API поверх DMA-буферов в физической памяти, на которую у приложения выдано право `devmap`; сокеты — чистый вызов функции LibOS, без IPC |
| Графика | **LVGL** (предпочтительно) или **Nuklear** | LibOS: GUI-библиотека; общий дисплей мультиплексирует compositor-приложение | framebuffer-память выделяется экзокосом как защищённый ресурс; прямой рендер в свою область окна без системных вызовов |
| Звук | **miniaudio** | LibOS: аудио-библиотека + HDA/USB-audio драйвер-либра | ring-buffer в разделяемой физической памяти; доступ к аудиорегистрам — по `iomap` от экзядро; микшер — отдельное LibOS-приложение |
| ФС | **FATFS** | LibOS: fs-библиотека (disk-as-file модель ExOS) | FATFS работает поверх `diskmap` — прямых прав на чтение/запись конкретных секторов диска; caching — в памяти приложения |

Все C-библиотеки **никогда не линкуются в ядро** — они являются частями LibOS/driver-libraries в адресном пространстве приложений. Экзядро только проверяет и выдаёт права на protected resources (секторы, порты, IRQ, страницы), поэтому сбои драйверов изолированы, а ядро остаётся чистым Carp-кодом.

## 4. Подробные задачи по модулям

### 4.1. Toolchain и загрузка (Boot)
- [ ] Выбрать целевые архитектуры: первая — **x86_64 (QEMU)**, вторая — **i386**, далее ARM.
- [ ] Настроить сборку Carp → C → объектные файлы ядра (karpet/carp CLI + кросс-компилятор gcc/clang, линковочный скрипт).
- [ ] Bootstrap на ассемблере: MBR/multiboot2-заголовок, переход в protected mode (32-bit) и long mode (64-bit), инициализация GDT/IDT, включение PAE/ paging.
- [ ] UEFI-загрузчик (опционально, этап 2) — GRUB multiboot2 как временное решение.
- [ ] Вывод serial/ VGA text-монитор для отладки ранних стадий.
- [ ] Проверка: ядро на Carp загружается в QEMU и печатает «Hello from Carp kernel» на 32 и 64 битах.

### 4.2. Экзядро на Carp (exokernel — только ресурсы и защита)
- [ ] **PMM (физический менеджер):** bitmap/freelist физических фреймов; выдача/возврат фреймов по запросу LibOS (`bind_physmem / free_physmem`) с учётом прав владельца.
- [ ] **Минимальный VMM ядра:** только kernel-адресное пространство + механизм загрузки пользовательских page tables, которые строит сам LibOS; запись таблиц в защищённую область, валидация экзокосом перед `load CR3`.
- [ ] **Page fault upcalls:** при fault ядро сохраняет регистры и делает upcall в обработчикfault'ов конкретного приложения (его LibOS), а не решает политику само.
- [ ] **Time-slice dispatch (НЕ планировщик):** ядро переключает контексты по кванту таймера (PIT/HPET/APIC timer) между «связанными» (bound) потоками времени; API: `bind_time(quantum) / yield / block(until_hw_event)`. Политики (RR, приоритеты) — полностью в LibOS.
- [ ] **Protected resources и права (модель Aegis):** таблица прав на: IRQ (`irqmap`), PIO/MMIO-порты (`iomap`), секторы/области диска (`diskmap`), DMA-страницы (`devmap`), физпамять, время CPU. Выдача/revocation/дедупликация прав; проверка на каждом syscall.
- [ ] **IRQ upcalls:** маршрутизация прерываний напрямую в handler зарегистрированного (по `irqmap`) приложения/LibOS; mask/ack/send-IPI syscall'ами.
- [ ] **Trap/exception forwarding:** деление на ноль, page fault, GP-fault → upcall в адресное пространство виновного приложения (его LibOS решает: перезапустить, убить поток, сообщить).
- [ ] **Загрузчик экзокос-модулей:** парсинг ELF32/ELF64, начальная раздача ресурсов первому процессу (init-LibOS), который дальше раздаёт права остальным.
- [ ] **Системный вызов ABI:** документированный набор примитивов: physmem, pgdir-load, time, irq, io, disk, ipc-lightweight (разделяемая память + doorbell — опционально, для взаимодействия приложений-серверов вроде compositor↔клиенты).
- [ ] Тестирование ядра: unit-тесты на хосте (Carp test) + интеграционные тесты в QEMU (проверка, что приложение НЕ может прочитать чужой сектор/порт/страницу).

### 4.3. LibOS (пользовательская системная библиотека — другие Lisp'ы; «серверная ОС»)
- [ ] Минимальный **C-runtime shim** (для линковки lwIP/FATFS/miniaudio/LVGL в состав LibOS).
- [ ] **Экзокос bindings** для каждого диалекта:
  - Racket: нативный компилированный раннер + FFI над exokernel ABI.
  - SBCL/Common Lisp: CFFI поверх syscall-шим.
  - Clojure: GraalVM native-image либо мост через Racket; вариант — Fennel как лёгкий диалект.
  - Guile: libguile встроенным интерпретатором в образе системы.
  - Fennel: компилируется в Lua → C (LuaJIT embed) — самый дешёвый путь к embedded-Lisp-приложениям.
- [ ] **Планировщик (политики) — здесь, а не в ядре:** пользовательский scheduler на Lisp поверх time-slice примитивов ядра: green threads / лёгкие процессы (акторы в стиле Erlang/CAPI), round-robin, приоритетные очереди, мультисинк-ожидания (wait на IRQ-upcall+таймер+IO в одной точке). Ядро лишь крутит контексты по кванту и выполняет `bind_time/yield/block`.
- [ ] **LibOS-VMM:** свой виртуальный менеджер памяти приложения — обработка page-fault upcalls, запрос фреймов у экзядро, стратегии (copy-on-write, swap, huge pages) выбирает LibOS.
- [ ] **Driver-libraries:** USB (cherryUSB/tinyUSB), NIC+lwIP, GPU/framebuffer+LVGL/Nuklear, audio+miniaudio, disk+FATFS — линкуются внутрь приложений; обращение к железу напрямую через полученные права `iomap/irqmap/diskmap/devmap`.
- [ ] Стандартные обёртки: файлы, сокеты, окна, аудио-стримы — единый Lisp-API (вызовы функций, не IPC-раундтрипы).
- [ ] **Lisp REPL как системный shell:** boot-REPL (можно на Carp-интерпретаторе или Fennel), из которого запускаются сервисы и приложения.
- [ ] Пакетный менеджер/система сборки приложений (компиляция Lisp → ELF-модули + манифест запрашиваемых protected resources).

### 4.4. USB (cherryUSB / tinyUSB — driver-library в LibOS)
- [ ] Выбрать: **cherryUSB** (легче для bare-metal, меньше зависимостей) как основной; tinyUSB как альтернатива для x86 EHCI/xHCI-стека.
- [ ] Транспортный слой: OHCI/EHCI/xHCI (PCI-enumeration + DMA) — для начала эмулируемый контроллер QEMU (piix3-usb-uhci / nec-usb-xhci). Приложение-владелец получает `iomap` на BAR контроллера и `irqmap` на его IRQ.
- [ ] Классы устройств (приоритет): HID (клавиатура/мышь) → mass storage (для FATFS) → CDC-serial (отладка).
- [ ] USB-хост-приложение (одно из LibOS-приложений владеет контроллером) раздаёт устройства клиентам через лёгкий IPC/doorbell-протокол; hot-plug события рассылаются подписчикам.
- [ ] Интеграция: клавиатура/мышь → GUI-compositor; mass storage → приложения с `diskmap`.

### 4.5. Сеть (lwIP — сетевая библиотека LibOS)
- [ ] Встроить lwIP в LibOS (no-OS config); примитивы синхронизации — поверх green threads планировщика LibOS.
- [ ] Ethernet-драйверы-библиотеки: RTL8139 / e1000 / virtio-net (QEMU-first); DMA-буферы — фреймы, выданные экзокосом по `devmap` NIC-приложению.
- [ ] Стек: DHCP + статическая конфигурация, ICMP, TCP/UDP raw API.
- [ ] Sockets-совместимый API поверх netconn как обычная библиотечная вызываемая функция LibOS; сетевой сервер (NAT/шлюз) — опциональное приложение-сервер для совместного доступа к одному NIC.
- [ ] Сервисы первого уровня: telnet/HTTP-сервер на Lisp (удалённая REPL-отладка ОС — ключевой debug-инструмент).

### 4.6. Графика (LVGL или Nuklear — GUI-библиотека LibOS)
- [ ] Фреймбуфер: VESA/VBE → затем GOP (UEFI) → затем GPU (virtio-gpu); физическая область fb защищается экзокосом и мультиплексируется compositor-приложением.
- [ ] **LVGL** как основной UI-стек (богаче widgets, лицензия MIT): рендер в offscreen buffer, blit в свою область fb. Nuklear — резервный вариант для лёгких тулзов (меньше RAM).
- [ ] Compositor-приложение (обычное LibOS-приложение, не часть ядра): список окон, focus, маршрутизация ввода от USB-приложения; прямые отображения (direct window mapping) — классическая экзокос-оптимизация.
- [ ] GUI-API в LibOS: окна/виджеты из Lisp — библиотечные вызовы + редкие обращения к compositor за координацию.
- [ ] Шрифты, темы, basic desktop на Lisp (рабочий стол = приложение, а не часть ядра).

### 4.7. Звук (miniaudio — аудио-библиотека LibOS)
- [ ] Встроить miniaudio (single-file) в LibOS; backend-драйвер: HDAC/HDA Intel (QEMU `ich9-intel-hda`) через `iomap` на HDA-регистры, позже USB-audio через USB-приложение.
- [ ] Software-микшер: отдельное mixer-приложение (N PCM-потоков от приложений → один выходной device callback) — политика микширования выбирается пользователем, не ядром.
- [ ] Транспорт: ring-buffer в разделяемой физической памяти (экзокос выдаёт общий фрейм обоим владельцам), doorbell-сигналы для start/stop/volume.
- [ ] LibOS-API: `play-sample`, `open-stream`, микширование/громкость.

### 4.8. Файловая система (FATFS — fs-библиотека LibOS, disk-as-file)
- [ ] Блочный доступ: virtio-blk / AHCI (SATA) / USB mass-storage; приложение запрашивает у экзядро `diskmap` на нужные сектора/разделы (защита — на уровне секторов, как в ExOS).
- [ ] FATFS внутри LibOS: mount/unmount, кэш, разделы (MBR/GPT) — всё в адресном пространстве приложения-владельца.
- [ ] **VFS-слой LibOS:** единый POSIX-подобный API (open/read/write/stat/readdir) поверх FATFS; точка расширения для будущих ФС (ext2/Lisp-native ФС); сетевой/расшаренный доступ — через fs-сервер-приложение (по желанию), а не через ядро.
- [ ] Автосбор: загрузочный образ диска с /boot (модули экзядра и приложений), /lisp (runtime'ы), /home.
- [ ] LibOS file API + сериализация путей, права — protected-resource манифестом модуля.

### 4.9. Сборка, CI, эмуляция
- [ ] Единая сборка: Makefile/Ninja + скрипты: carp-компиляция экзядра → сборка LibOS (C-библиотеки cherryUSB/lwIP/LVGL/miniaudio/FATFS + Lisp-слой) → Lisp-компиляция приложений (ELF + манифест ресурсов) → образ ISO/QEMU-диск.
- [ ] QEMU-скрипты запуска: `-machine q35 -cpu max`, serial stdio, e1000/virtio-net, usb devices, hda.
- [ ] CI: сборка + smoke-тест (экзядро грузится, init-LibOS стартует, приложения получают ресурсы, REPL отвечает по telnet).
- [ ] Документация экзокос ABI (syscall + protected resources + upcalls) — ver 1.0 freeze до начала массового писания LibOS.

## 5. Этапы разработки (roadmap)

| Этап | Содержание | Критерий готовности |
|---|---|---|
| **M0** | Boot, PMM (раздача физ. фреймов), serial print, QEMU 32/64 | Экзядро Carp грузится, приложение получает фреймы по запросу, panic-trace |
| **M1** | Time-slice dispatch, upcalls (faults/IRQ), загрузчик ELF + init-LibOS | Приложение со своим LibOS обрабатывает page fault и IRQ; таймер крутит контексты (политики — в LibOS) |
| **M2** | Protected resources: `iomap`/`irqmap`/`diskmap`/`devmap` + PCI enumeration | Два приложения независимо владеют разными портами/секторами; попытки захвата чужого ресурса отклоняются |
| **M3** | USB driver-library (cherryUSB) + HID | Клавиатура/мышь работают через приложение-владельца контроллера, события раздаются клиентам |
| **M4** | FATFS-библиотека поверх `diskmap` | Чтение/запись файлов напрямую из приложения; загрузка модулей с диска |
| **M5** | lwIP-библиотека + NIC-драйвер + remote REPL | telnet-REPL извне; ping/DHCP — всё внутри LibOS без сетевых серверов ядра |
| **M6** | LVGL + compositor-приложение | Окна, прямой рендер приложения в свою область fb, вывод Lisp-приложения в GUI |
| **M7** | miniaudio + mixer-приложение | Воспроизведение WAV из Lisp-приложения через shared ring-buffer |
| **M8** | LibOS на Racket/SBCL/Fennel/Clojure + Lisp-планировщик (политики) | Полноценные Lisp-приложения поверх экзокос ABI; green threads/акторы, RR и приоритеты в LibOS |
| **M9** | Стабилизация, второй CPU backend (ARM), безопасность | SMP (per-CPU time-slices), аудит прав protected resources, переносимость |

## 6. Правила для агентов-разработчиков

1. **Ядро — только Carp.** Любой C-код допускается лишь в `boot/` (asm/stub) и как внешние библиотеки внутри LibOS/driver-libraries. Код ядра, прошедший ревью, компилируется karpet→C без ручных правок сгенерированного C.
2. **LibOS и приложения — Lisp** (Racket / SBCL / Clojure / Guile / Fennel). Пишем логику ОС верхнего уровня на Lisp, а не на C.
3. **Экзокос-принцип: ядро не абстрагирует.** В ядре запрещено: планирование политик, кэширование ФС, сокеты, оконная система, драйверы устройств. Ядро только выдаёт/проверяет права на protected resources и делает upcalls. Каждая C-библиотека (cherryUSB/tinyUSB, lwIP, LVGL/Nuklear, miniaudio, FATFS) линкуется в состав LibOS как driver-/system-library; наружу из приложения — библиотечный API, внутрь к железу — прямые права `iomap/irqmap/diskmap/devmap`.
4. Все syscall-интерфейсы (экзокос ABI) документируются до реализации; ABI не ломается без мажорной версии.
5. Каждый модуль имеет тесты: хостовые (unit) + QEMU (integration), включая negative-тесты защиты ресурсов.
6. Предпочтение читаемости и малому объёму кода: exokernel-минимализм ядра, вся сложность — в LibOS и приложениях.
7. Отладочный контур: remote Lisp REPL поверх lwIP считается обязательным инструментом с этапа M5.
